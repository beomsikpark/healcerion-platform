# 변경 1건의 실제 비용 — 실측

> **이 문서의 역할**: 다른 문서의 "효과" 주장은 전부 여기로 수렴한다. 파일 수·LOC 같은 개발자 단위가 아니라 **재작업·출하 지연·제품 미도달** 로 잰다.
>
> **측정 원칙**: 전부 그들 git 이력에서 식별자 수준으로 확정했다(커밋 SHA · patch-id · 브랜치 도달성). 추정치는 넣지 않는다. **논지에 불리한 결과도 그대로 적는다** — 그것이 빠지면 나머지가 근거가 아니라 광고가 된다.
>
> 측정 시점 2026-07-28. 재현 명령은 §7.

`origin/production-fw-ver2.0` 기준 22/66(33%)이 미도달이다. **비율만 보면 `moana` 보다 나쁘지만, 내용을 보면 아니다.**

| 브랜치 | 커밋 | 최종 | 정체 |
|---|---:|---|---|

**거의 전부 정당한 사유가 있다** — 별도 제품라인이거나, 아직 끝나지 않은 R&D다. `T1968` 은 마지막 커밋이 `T1968 CF 공간적분 일괄 롤백 — 브랜치 분기점(0c196ac) 코드로 복원` 이다. **시도했다가 되돌린 실험**이고, 이것은 정상적인 연구 활동이지 낭비가 아니다.

### 3.1 다만 여기서 다른 비용이 보인다

`T1968` 8커밋 중 실제 알고리즘 변경은 3건이고, **나머지는 진단·로그 추가와 롤백**이다.

```
T1968 진단: cf_process 출력 통계 로그 추가
T1968 진단: cf_process 호출 직전 power_window 로그 추가
T1968 CF 게이트 진단 추가: 무엇이 검출을 좌우하는지 정량화
T1968 CF 공간적분 일괄 롤백 — 브랜치 분기점 코드로 복원
```

**측정 수단이 없어서 로그를 손으로 심어 관측하고 있다.** 알고리즘을 바꾸고 그 결과를 재는 oracle 이 있었다면 이 4커밋의 성격이 달라진다. FPGA 팀은 같은 문제를 비트정확 골든 모델(`ginny-renewal/model/src/*.c`)로 이미 풀어 두었다 — **사내에 방법이 있는데 장비 쪽에 없다.**

> 이것은 "브랜치 낭비"가 아니라 **"검증 수단 부재"** 의 증거다. 성격이 다르므로 구분해 적는다.

## 5. 그들이 이미 개선한 것 — 인용하지 않을 근거

**릴리스 규율은 현재 문제가 아니다.**

태그 71개 중 `M2.00.00` 계열이 **22개**다 — `M2.00.00_SQA` 와 `a`~`u` 재출시 21개. 2019-08-16 ~ 2020-05-26, **9개월간 한 버전을 21번 다시 냈다.** `20200218_라온즈_전달` → `20200225_라온즈_재전달` 은 **8일 만의 재전달**이다.

**그런데 `M2.00.18b`(2022-05-10) 이후 letter 재출시 태그가 하나도 없다.** 이후 `M2.00.19`~`M2.03.25` 까지 전부 단발이다.

| 지금도 남아 있는 것 | 실측 |
|---|---|
| 플랫폼별 별도 릴리스 | `M2.00.17_for_Windows` · `M2.00.18_for_Android` — 단일 코드베이스인데 타깃별 태그가 갈린다 |

| 릴리스 간격 | `M2.03.24`(2026-01-16) → `M2.03.25`(2026-07-02) = **5.5개월** |

그리고 출하 브랜치 비병합 커밋 4,625건 중 **`[SQA]` 표기가 150건**이다. **사내 QA 가 잡아낸 것이 기록으로 남아 있다** — 회귀 안전망이 전무하다는 서술은 사실과 다르다. 없는 것은 **자동화된 회귀 판정**이지 QA 자체가 아니다.

> **§5 는 우리 논지에 불리하다.** 재출시 폭풍을 현재 고통으로 인용하면 6~7년 전 데이터를 현재로 파는 것이 된다. 하지 않는다. 대신 이 사실은 **"역량이 아니라 배치 문제"의 근거**로 쓴다 — 릴리스 규율을 스스로 세운 조직인데, 그 규율이 장비·기반·이음매 축에는 적용된 적이 없다.

## 7. 효과의 상한 — E2E 가 실제로 잡을 수 있는 회귀인가

> **이 절이 없으면 "회귀를 커밋 시점에 잡는다"는 근거 없는 미래형이다.** 효과는 만들기 전에는 직접 측정할 수 없다. 대신 **과거 회귀를 표본으로 잡아 제안한 E2E 의 범위에 드는지 분류하면 상한이 나온다.**

### 7.1 표본과 분류 방법

`moana` 출하 브랜치(`service_QT693`)의 **2026-06-24 ~ 2026-07-27 커밋 43건 전량**에서 버전 상향·빌드 설정·문서·기능 추가를 뺀 **결함 수정 16건**이다. 구간을 먼저 정하고 전량을 넣었다 — 골라 담지 않았다.

분류는 판단이 아니라 **변경 파일 계층**으로 한다. 제안한 E2E 는 장비↔앱↔클라우드 **데이터 경로**를 개발 PC 에서 실행하는 것이므로([../refactoring/emulator-e2e.md](../refactoring/emulator-e2e.md)), 그것이 닿는 계층은 `framework/` 다. `.qml` 만 바뀐 것은 표시 계층이라 닿지 않는다.

### 7.2 결과

| 분류 | 건수 | 비율 |
|---|---:|---:|
| **`framework/` 를 건드림** — 데이터 경로 E2E 범위 안 | **4** | **25%** |
| **`.qml` 만 건드림** — 순수 표시 계층, 범위 밖 | **7** | **44%** |
| 그 외 (`app/Sources` 만) | 5 | 31% |

| `4e0bc03f0` CF→PW 전환 후 리뷰이미지에 CF 컬러 섞임 | `ScanPlayer.cpp` 1파일 | **잡힐 수 있다** — 프레임 내용 비교 |

### 7.3 결론 — 효과를 좁혀 적어야 한다

**제안한 E2E 가 도달하는 회귀는 최근 표본의 약 1/4이다.** 나머지는 성격이 다르다.

| 회귀 성격 | 비중 | 제안한 E2E 로 |
|---|---:|---|
| 데이터 경로 (영상 변환·저장·프레임 상태) | 25% | **잡힌다** |
| **Qt/QML UI 상태 기계** (듀얼모드 전환·Freeze/Unfreeze·위젯 가시성·재진입) | **44%** | **못 잡는다.** UI 테스트라는 **별도 투자**가 필요하고 현 제안에 없다 |
| 성능·플랫폼 고유 (FPS 널뜀 · Android SAF · 300C/Windows/iOS 렌더링) | 일부 | **원리적으로 못 잡는다** — 개발 PC 가 실장비 타이밍을 재현하지 않는다 |

**즉 "E2E 를 만들면 회귀가 출하 전에 잡힌다"는 서술은 과장이다.** 정확한 서술은 **"데이터 경로 회귀에 한해 자동 판정이 생긴다"** 이고, 그들이 최근 실제로 고친 회귀의 과반은 그 범위 밖이다.

### 7.4 이 측정의 한계

- **표본이 16건·1개월이다.** 일반화할 수 없다. 구간을 넓히면 비율이 달라질 수 있다
- **심각도를 재지 않았다.** 25%에 속한 `f32880464`(PACS 이미지 손상)는 환자 데이터 무결성 문제이고, 44%의 위젯 미표시와 같은 무게가 아니다. **건수 비율이 가치 비율은 아니다**
- **장비 축은 이 표본에 없다.** `belle-fw` 는 같은 구간에 비교할 수정 이력이 없다. 장비 쪽 E2E 효과는 **미측정**이다
- `moana` 는 이미 Windows·macOS 로 빌드되므로 **Qt/QML UI 테스트를 개발 PC 에서 붙이는 경로는 존재한다.** 다만 그것은 장비 에뮬레이터와 별개 투자이고, 현 제안에 포함돼 있지 않다

- 제목 정규식 기반 분류(수정 커밋 비율 등)는 잡음이 커서 **폐기했다** — `개선`·티켓 반복 커밋이 섞여 의미가 없다
