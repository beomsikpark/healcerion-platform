## 1. 제안 3건에 대한 판단

### 1.1 SDK 를 빌드 가능한 형태로 — **동의. 다만 문제가 둘이다**

제안대로 우선순위 1순위가 맞다. 다만 "SDK 가 바이너리" 라는 진단을 쪼개면 **성격이 다른 두 문제**이고, 해법도 다르다.

| # | 문제 | 실측 | 해법 |
|---|---|---|---|
| **A** | **앱↔SDK 인계가 수작업이다** | `sonex-app/scripts/copy_sdk_dlls.ps1:9` 이 `C:\work\flutter\sonex-framework\sdk\_out\x64\bin\Release` 에서 복사. iOS·macOS 는 `.rb` 스크립트가 `/Users/rio/...` 에서 주입. Android 는 `.so` **41개를 앱 저장소에 커밋** | **CI 에서 SDK 를 빌드해 버전 태그된 아티팩트로 발행**하고, 앱은 버전을 고정해 가져온다 |
| **B** | **서드파티가 플랫폼별 프리빌트로 커밋돼 있다** | `sonex-framework/sdk/adk/library` **1.1G** · `moana/lib` **6.1G**. OpenCV·DCMTK·FFmpeg·TFLite 를 플랫폼 7종별로 각각 | **재현 가능한 획득**(vcpkg/Conan 또는 사내 아티팩트 저장소 + 버전 고정). **소스 빌드가 목표가 아니다** |

**A 가 진짜 문제다.** SDK 자체(`sonex-framework`·`moana/framework`)는 이미 소스로 빌드된다. 끊긴 것은 **앱이 그 산출물을 받는 경로**이고, 지금은 특정 개발자 머신 경로에 의존한다. **어느 앱 빌드가 어느 SDK 빌드와 짝인지 저장소에서 확인할 방법이 없다.**

**B 는 "빌드 가능하게" 가 답이 아니다.** OpenCV·FFmpeg·DCMTK 를 7개 플랫폼용으로 매번 소스 빌드하면 CI 시간이 수 시간대로 늘고 얻는 게 없다. 필요한 것은 **출처·버전·해시가 고정된 획득 절차**다. IEC 62304 의 SOUP 관리 요구와도 이쪽이 맞는다.

부수 효과가 크다 — `moana` 9.4GB 중 자체 소스는 8MB 미만이다. B 를 정리하면 **클론·CI·브랜치 비용이 전부 내려간다.**

### 1.2 서버는 비용 확인 후 보류 — **동의. 단, 비용과 무관한 조치 2건은 지금 해야 한다**

리팩토링을 미루는 판단에 동의한다. 근거도 뒷받침된다 — `sonex-cloud-backend` 는 **4년간 4커밋**, `sonex-admin-web` 은 **커밋 1개**, `sonon-cloud/admin-dashboard` 는 **2021-08 이후 정지**다. 손대도 얻을 게 적고 위험만 는다.

**다만 비용 판단과 별개인 위험이 둘 있다.**

| 항목 | 위험 | 비용 |
|---|---|---|
| **비밀정보 커밋** | MariaDB **root 비밀번호**가 5개 파일에(`DatabaseConfig.xml` 은 `sonex.healcerion.com` / `root` / 평문), **GCP 서비스 계정 개인키**가 git 에 있다(`functions/sharp-imprint-234606-*.json`). 후자는 **현재 운영 중인 시스템**의 키다 | 키 교체 — 시간 단위 |
| **`sdi`·`ela` 스키마 DDL 이 `.sql` 로는 없다** | 매퍼가 호출하는 저장 프로시저 53건의 정의가 `query script/` 에 없다 | **`.mwb` 에서 추출** — 시간 단위 |

> **두 번째 항목의 초기 판단(재구축 불가)은 과장이었다.** `.sql` 스크립트는 `cloud`·`sso` 만 있지만, **`Database server/schema design/schema design.mwb`(MySQL Workbench 모델, 2023-01-11)에 5개 스키마가 전부 들어 있다** — `cdi`·`cloud`·`ela`·`sdi`·`sso`.
>
> | | 테이블 | 프로시저(`sqlDefinition` 본문 포함) |
> |---|---:|---:|
> | `sdi` | 8 | 35 |
> | `ela` | 4 | 24 |
> | `sso` | 15 | 46 |
> | `cloud` | 3 | 6 |
>
> 매퍼 호출과 대조하면 **SDI 33/33 · SSO 42/42 · cloud 3/3 · ELA 18/20** — 없는 것은 `sp_GetGroupEventList`·`sp_SetGroupEventList` **2건뿐**이다(2026-07-28 실측, `.mwb` 를 XML 로 풀어 대조).
>
> 따라서 **복구 경로가 "운영 DB 덤프" 가 아니라 "모델에서 DDL 생성" 이다.** 다만 위험이 0 은 아니다 — ELA 2건과 **운영 데이터**는 여전히 저장소 밖이다. `schema (sonex).mwb` 는 MD5 동일한 사본이다.

**여전히 사업 연속성 이슈다.** "안 건드린다" 는 결정과 "복구할 수 없다" 는 상태는 다르다 — 다만 남은 간격이 좁고, 그래서 **지금 닫는 것이 싸다.**

그리고 방치된 서버가 **여전히 제품 경로에 있다** — `moana` 가 디바이스·배터리 등록을 이 서버로 한다([../review/protocol-cloud.md §3](../review/protocol-cloud.md)). 끊긴 게 아니라 쓰이면서 방치된 상태다.

### 1.3 장치에 Buildroot 도입 — **동의. 그리고 이것이 빌드 재현의 수단이다**

처음에 "아티팩트 복구 뒤로 미루자" 고 봤으나, **근거 둘이 틀렸다.**

**틀린 근거 1 — 규제**: "빌드 시스템 교체는 전체 재검증 사유" 라고 썼는데, 이 프로젝트는 **애초에 리팩토링**이라 재검증 비용이 이미 계상돼 있다. 별도 장벽이 아니다.

**틀린 근거 2 — FSBL 블로커**: FSBL 소스 부재를 부팅 블로커로 봤으나 우회 경로가 있다.

| 확인 | 위치 |
|---|---|
| **`psu_init_gpl.c`**(17,791줄, MIT) — PS 초기화 시퀀스, 보드 고유부 | `belle-bsp/project-spec/hw-description/` |
| **`CONFIG_SPL=y`** + `SPL_SPI_FLASH_SUPPORT` + `SPL_LOAD_FIT` | `belle-u-boot/configs/xilinx_zynqmp_virt_defconfig` |

**ZynqMP 에서 U-Boot SPL 이 Xilinx FSBL 을 대체할 수 있고, 그 SPL 은 이미 빌드되며 보드 고유 PS 초기화 코드도 저장소에 있다.** FSBL 저장소가 비어 있는 것은 부팅을 막지 않는다.

### Buildroot 가 문제를 우회가 아니라 해결로 만든다

`BR2_EXTERNAL` custom package 트리를 만드는 것이 **지금 깨져 있는 것들을 강제로 고치게 한다.**

| 현재 문제 | custom package 화하면 |
|---|---|
| 커널 모듈 3종에 **Makefile 없음** | 패키지로 만들려면 **써야 한다.** 우회가 불가능 |
| `EXTERNALSRC` 가 `/home/jacob/...` 절대경로 | 패키지 정의가 소스 위치를 명시한다. 절대경로가 설 자리가 없다 |
| `NE10` 이 헤더만 있고 `.a` 는 어디선가 | 패키지로 빌드하거나 출처를 명시해야 한다 |
| `release_elsa.sh` 의 수동 단계(`sudo mkfs.ubifs`) | `post-image` 스크립트로 흡수 |
| PetaLinux 버전 미확정 | Buildroot 는 `defconfig` 하나로 고정된다 |
| rootfs 가 외부 `petalinux-image-minimal` | `BR2_ROOTFS_OVERLAY` + 패키지 선택으로 저장소 안에 들어온다 |

**즉 "빌드 재현 뒤에 Buildroot" 가 아니라 "Buildroot 가 빌드 재현의 방법" 이다.** PetaLinux 를 재현하려면 없는 PetaLinux 아티팩트·버전을 복구해야 하지만, Buildroot 로 가면 **이미 있는 소스로 패키지를 정의**하면 된다.

### 남는 진짜 블로커는 하나다

| 항목 | 상태 |
|---|---|
| **PL 비트스트림 재생성** | `.xsa` 원본 Vivado 프로젝트가 없다. **하드웨어 설계 변경이 불가**하다 |
| 기존 비트스트림 사용 | `configs/500l/top_osc40_cmos_221018.bin`(IDCODE `0x04a42093`)을 그대로 패키징하면 **빌드는 된다** |
| PMU 펌웨어 | 프리빌트 ELF 존재. Buildroot 는 `BR2_TARGET_UBOOT_ZYNQMP_PMUFW` 로 임베드 가능 |
| 디바이스 트리 | `.xsa` 자동 생성 대신 **DTS 를 저장소에서 관리**. `system-user.dtsi` 가 이미 있어 출발점이 된다 |

**PL 설계를 안 바꾸는 한 Buildroot 전환에 `.xsa` 원본은 필요 없다.** Vivado 프로젝트는 여전히 요청 대상이되, **빌드 재현의 전제 조건은 아니다.**

### 유리한 조건

rootfs 가 initramfs(RAM), 플래시 118MiB QSPI, 앱 오버레이 10MiB — **Buildroot 의 강점 구간**이다. 그리고 A/B 뱅크 구조를 `post-image` 로 그대로 재현할 수 있다.

## 2. 내 추가 판단 — 먼저 해야 할 것

### 2.1 최우선: 프로토콜 정본 단일화

**위험이 가장 낮고 효과가 가장 크다.**

- 헤더 선언 **3벌**(`belle-fw/sonon/sonon_receive.h:2210` · `moana/framework/SononClient/SononPacket.h` · `500c-sn-fw`)
- opcode 명명 규약이 **장비와 앱에서 서로 다르다** — 장비는 `READ`/`WRITE` 쌍, 앱은 쌍 중 하나만 이름 붙임. 같은 값에 다른 이름이 8건
- 앱이 모르는 `packet_type` 3개
- **CRC 가 없다** — `verify_packet_header_and_crc` 함수명과 달리 검사 코드 없음

**왜 먼저인가**: 빌드 재현 없이도 할 수 있는 거의 유일한 항목이다. 헤더 하나를 뽑아 양쪽이 include 하게 하는 것은 동작을 바꾸지 않으며, 바이트 배치가 이미 같다는 것이 검증돼 있다. 그리고 이후 모든 작업이 이 인터페이스 위에서 이뤄진다.

### 2.2 개발 PC E2E — 빌드 재현과 **같이** 간다

빌드가 재현되면 곧바로 필요한 것이 "그래서 맞게 만들어졌나" 다. 둘을 순차로 두면 안 된다. 그리고 **실장비 없이 검증되지 않으면 CI 에서 돌릴 수 없다.**

**착수 비용이 낮다.** 만들 것은 **HC 프로토콜을 말하는 장비 시뮬레이터** 하나이고, 포트 1234/1235 에서 녹화 데이터를 프레임으로 흘리면 앱 전 경로가 검증된다. 프로토콜 정의·녹화 포맷·시나리오 러너·더미 vtable 이 이미 있다.

**설계·자산 목록·각 자산의 한계 = [emulator-e2e.md](emulator-e2e.md).** 여기서 반복하지 않는다.

판단상 중요한 것 둘만 적는다.

| | |
|---|---|
| **선행 조건이 없다** | 독립 시뮬레이터(경로 A)는 프로토콜 정본만 있으면 만들 수 있다. 빌드 재현·`core/ports` 를 기다리지 않으므로 **§2.1 바로 다음**이다 |
| **`sonon-simul`(id 33) 확인이 먼저다** | "Sonon Graymap Simulator". **미클론**이고 범위 제외 판단의 재검토 대상이다. 이미 만들어진 시뮬레이터라면 착수 범위가 달라진다 |

### 2.3 Qt → Flutter 전환은 결정 사항이다 — 평가가 아니라 지원이 과제다

**전환 여부는 회사 결정이므로 검토 대상이 아니다.** 그러면 남는 질문이 바뀐다 — "할 것인가" 가 아니라 **"어떻게 안전하게 끝낼 것인가"** 다.

여기서 두 저장소의 역할이 갈린다.

| | 역할 |
|---|---|
| **`moana`** | **사양 정본(SOT)** — 제품이 무엇을 하는지의 기준. 그리고 **전환 완료까지 출하되는 현물** |
| **`sonex`** | **전환 목표** — 최종적으로 `moana` 를 대체한다 |

`moana` 가 SOT 인 것은 **"최종 목표" 라는 뜻이 아니라 "동작의 기준" 이라는 뜻**이다. sonex 가 무엇을 만족해야 하는지는 moana 가 정의한다.

### 투자 배분이 여기서 갈린다

> **이 항목의 초기 판단(`moana` 는 손대지 않는다)은 뒤집혔다.** 대체될 코드베이스라는 이유로 방치하면, `sonex` 가 **83k LOC 의 `Scan/` 을 뒤지며 사양을 복원**해야 한다. `moana` 정리는 `moana` 에 대한 투자가 아니라 **이식 비용을 낮추는 선행 공정**이다. 근거 = [architecture.md §4.3](architecture.md).

| 대상 | 원칙 |
|---|---|
| `moana` 내부 구조 | **feature 단위로 정리한다 — 다만 이식할 feature 에 한해, 이식 직전에.** 골격은 이미 feature 로 나뉘어 있어(`Scan`·`Measure`·`PatientList`…) 남은 일은 `Scan/` 분해와 계층 분리다 |
| `moana` 도메인 지식 | **뽑아낸다.** 측정 8종·프리셋·DICOM/MWL·PACS·환자기록·Ambulance 의 동작 사양이 전환의 입력이다. **정리 과정에서 부산물로 나온다** |
| `moana` 신호처리·렌더링 | **다시 쓰지 않는다.** 위치만 옮긴다 |
| `sonex` | 구조 투자의 최종 목적지. 정리된 feature 를 **하나씩** 받는다 |
| 공유 계층 | 프로토콜 정의는 **장비 쪽이 공유**하므로 전환과 무관하게 단일화한다(§2.1) |

**"moana 를 전면 리팩토링한다" 가 아니다.** 판정 기준은 하나다 — `moana` 쪽 작업이 **그 feature 의 sonex 이식을 더 싸게 만드는가**. 아니면 하지 않는다.

### 기능 격차 실측은 여전히 필요하다 — 성격이 다를 뿐

판단 근거가 아니라 **전환 백로그**로서 필요하다. moana 에 있고 sonex 에 없는 것이 곧 남은 작업이다.

| moana 도메인 기능 | 규모 | sonex 대응 |
|---|---|---|
| 측정·캘리퍼 8종(모드별 분리) | 50파일 12.7k LOC | **미대조** |
| 환자·검사 기록 | 40+24파일 20.1k LOC | 미대조 |
| DICOM · PACS · MWL | 3.0k LOC | `DicomHandler` 존재, 완성도 미대조 |
| Ambulance(EMS, GPS 태그 업로드) | 39파일 14.9k LOC | 미대조 |
| BLE 페어링(500L/500P) | — | 미대조 |
| 지원 모델 | **10종** | **5종** |
| 출하 타깃 | Android·iOS·UWP | android·ios·macos·windows |

**모델 10종 → 5종, 그리고 UWP 부재**가 눈에 띈다. 전환 완료 조건에 이것들이 들어가는지가 정해져야 한다.

### 전환기에 생기는 비용을 인정하고 관리한다

전환이 끝날 때까지 **두 앱이 병존**하고, 그동안 다음이 이중으로 유지된다.

- 프로토콜 클라이언트 2벌(`moana/framework/SononClient` · `sonex-framework/DeviceManager`)
- NextSRI 필터 2벌 — 그들 문서가 **"1:1 포팅, 바이트 동일"** 로 기록
- 클라우드 연동 2벌

**이 비용을 없애려 하지 말고 기한을 정한다.** 전환 완료 목표가 없으면 병존이 영구화된다 — `sonex-app` 첫 커밋이 2024-04 이고 **2년 3개월간 도메인 이식 0건**이며, **완료 조건이 코드·저장소 문서 어디에도 없다**([../review/sonex-app.md §10](../review/sonex-app.md)).

그리고 이 판단은 시간이 갈수록 불리해진다 — 구 계층이 **분기당 +76%** 로 늘어 이식 대상이 계속 커진다. 5번 항목(기능 격차 실측)이 뒤로 밀릴수록 대조해야 할 양이 는다.

### 2.4 Qt 라이선스는 리스크가 아니라 확인 항목이다

`moana` 가 쓰는 Qt 모듈은 `quick qml sql network multimedia concurrent positioning quickcontrols2 widgets printsupport androidextras` 로 **전부 LGPLv3 계열**이고 GPL 전용 모듈이 없다. 상용이 **법적으로 필수는 아니다**.

실제로 확인할 것은 셋이다.

| 항목 | 이유 |
|---|---|
| Qt 상용 계약 범위 | `QtCommercial/5.15.2` 경로가 있다. LTS 패치 접근이 목적으로 보인다 |
| **QCustomPlot 라이선스** | `app/Sources/Scan/ImageAnalyzer/qcustomplot.cpp` 가 **GPL** 이다. Qt 보다 직접적인 리스크 |
| sonex 착수 동기 | 라이선스가 동기 중 하나였다면 전환 우선순위 근거가 된다. Flutter 는 BSD 라 이 항목이 자연 해소된다 |

### 2.5 클라우드 로컬 실행은 "보류" 대상이 아니다

§1.2 의 보류는 **리팩토링**에 대한 판단이다. **로컬에서 띄우는 것은 별개이고, 둘 다 가능하다** — 구조적으로 막는 것이 없다.

| | 로컬 실행 |
|---|---|
| `sonex-cloud-backend`(Java) | Tomcat + MariaDB. 스키마는 `.mwb` 에서 생성(§1.2). 접속 설정이 파일 하나 |
| `sonon-cloud`(Firebase) | 쓰는 서비스가 auth·firestore·storage **3종뿐이고 전부 에뮬레이터 지원**. `constants.js` 에 localhost 주석이 남아 있다 |
| 앱 연결 | base URL 하드코딩(sonex 7 · moana 5) → **설정 외부화. 어차피 우리 작업 항목** |

**스텁보다 실물이 낫다.** 스텁은 계약을 사람이 다시 적어야 하고 실제와 갈라진다. 상세 = [emulator-e2e.md §4](emulator-e2e.md).

저장소 밖에 남는 것은 **ELA 프로시저 2건 · 운영 시드 데이터 · SMTP** 셋뿐이고, 앞의 둘은 순서표 0번에서 닫는다.

## 3. 권장 순서

앞의 8단계가 **기반**이고, 뒤의 4단계가 **리팩토링 본체**다. 기반 없이 본체를 시작하면 회귀를 판정할 수 없다.

| 순서 | 항목 | 선행 조건 | 근거 |
|---|---|---|---|
| **0** | 비밀정보 교체 · **`.mwb` → DDL 추출** · ELA 2건 운영 덤프 | 없음 | 사업 연속성. 시간 단위 작업(§1.2) |
| **1** | **프로토콜 정본 단일화** | 없음 | 위험 최저·효과 최대. 빌드 없이 가능(§2.1) |
| **2** | **Buildroot `BR2_EXTERNAL` 도입** — `belle-fw`·커널 모듈 3종·`NE10` 을 custom package 로 | 없음 | **빌드 재현의 방법.** 없는 Makefile 을 강제로 쓰게 한다(§1.3) |
| **3** | **장비 시뮬레이터 + 앱 E2E** — 정본을 첫 소비 | 1번 | 실장비 없이 회귀 검증([emulator-e2e.md §2](emulator-e2e.md)) |
| **4** | **최소 CI** — 빌드가 도는 것부터, 이미 있는 테스트를 붙인다 | 2·3번 | **CI 가 31건 전부 0건.** 테스트는 있는데 아무도 안 돌린다 |
| **5** | **기능 격차 실측 → 전환 백로그** | 없음 | 전환 완료 조건 확정(§2.3) |
| **6** | 의존성 관리 도입 | 4번 | 7.2GB 정리(§1.1-B) |
| **7** | SDK 아티팩트 파이프라인 | 4·6번 | 앱↔SDK 버전 고정(§1.1-A) |
| **8** | **장비 `core/ports` + `platform/sim`** | 2·3번 | 펌웨어를 개발 PC 에서 실행([architecture.md §8](architecture.md)) |
| **9** | **장비 feature 분리** — `doppler_pw` 부터 | 4·8번 | 가장 흩어져 있다(§why 5-A) |
| **10** | **`moana`→`sonex` feature 파이프라인** — 얕은 것부터, `scan` 계열 마지막 | 4·5번 | 진척을 셀 수 있고 중간에 멈춰도 양쪽 정상([architecture.md §4.4](architecture.md)) |
| **11** | 런타임 변종 선택 복원 | 2·4번 | 사내 선례 있음(원칙 §7) |
| — | Vivado 프로젝트 확보 | 힐세리온 응답 | **하드웨어 변경 시 필요.** 빌드 재현의 전제는 아님 |
| — | 서버 리팩토링 | 비용 판단 | 보류(§1.2) |

**0·1·2 는 병렬 가능하다.** 2번이 끝나면 깨끗한 체크아웃에서 이미지가 나오고, 3·4번이 붙으면 그때부터 리팩토링(8~11)이 안전한 작업이 된다.

9번과 10번은 **서로 독립이라 병렬로 간다** — 장비 축과 클라이언트 축이 프로토콜 정본(1번)으로만 만나기 때문이다. 축을 동시에 흔들지 않는다는 원칙(원칙 §4)은 **인터페이스를 고정한 채**라는 조건에서 지켜진다.

## 4. 판단의 요지

제안 3건 중 **둘은 순서를 조정하면 그대로 맞다.**

- SDK — 우선순위는 맞다. **"소스 빌드" 가 아니라 "재현 가능한 획득 + 버전 고정"** 으로 목표를 잡아야 한다
- 서버 — **리팩토링** 보류가 맞다. 단 **로컬 실행은 보류 대상이 아니다**(§2.5). 비용과 무관한 2건도 지금 해야 한다
- Buildroot — **지금 해야 한다.** 처음 판단(뒤로 미루자)은 틀렸다. `BR2_EXTERNAL` custom package 를 만드는 것이 **없는 Makefile·절대경로·수동 단계를 강제로 걷어내는 방법**이고, `psu_init_gpl.c` + U-Boot SPL 로 FSBL 의존도 우회된다

그리고 **개발 PC full E2E** 는 원칙에 넣었다(원칙 §3). 더미 vtable·녹화 포맷·시나리오 러너가 이미 양쪽에 있어 **만들 것은 HC 프로토콜 시뮬레이터 하나**다. 이것이 없으면 회귀 검증이 CI 로 올라가지 못하고, 지금처럼 CS 로 회귀를 발견하게 된다.

**리팩토링 본체(8~11)를 순서표에 넣었다.** 기반만 적어두면 "언제 실제로 코드를 바꾸는가" 가 비어 보인다. 다만 순서는 바뀌지 않는다 — 기반이 서기 전의 구조 변경은 회귀를 판정할 수 없다.

그리고 **가장 먼저 할 수 있는 것은 프로토콜 정본 단일화**다. 다른 모든 항목이 외부 응답(아티팩트)이나 선행 결정(sonex 존폐)을 기다리는 동안, 이것만은 지금 바로 착수할 수 있고 위험이 거의 없다.
