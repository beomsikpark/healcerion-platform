# 리팩토링 원칙

> **전제**: 현행 구조 분석은 [../review/](../review/) 가 SOT 다. 이 문서는 그 위에서 **무엇을 지키며 바꿀 것인가**를 정한다.
> **범위**: belle(500L) 장비 · `moana`(**사양 정본이자 현행 출하물**) · `sonex`(**전환 목표**, Qt→Flutter 는 회사 결정 사항) · 클라우드.

## 0. 이 리팩토링의 특수 조건

일반적인 코드 정리와 다른 조건이 셋 있다. 원칙은 전부 여기서 나온다.

| 조건 | 실측 근거 |
|---|---|
| **빌드를 재현할 수 없다** | FSBL·PMU 소스 없음(저장소가 빔) · `.xsa` 원본 Vivado 프로젝트 없음 · 커널 모듈 3종에 Makefile 없음 · 절대경로 `/home/jacob/...` 의존 |
| **자동 회귀 판정이 없다** | belle 계열·`moana` 자동 테스트 0건. **CI 는 31개 저장소 전부 0건** — `sonex-app`(2,518 LOC)·`sonon-cloud/functions/test` 에 테스트가 있어도 아무도 돌리지 않는다. **다만 사내 QA 는 돌고 있다**(`[SQA]` 150건) — 없는 것은 안전망이 아니라 자동화다 |
| **의료기기다** | IEC 62304 / ISO 14971. 변경마다 영향분석·검증 기록이 따라붙는다 |

## 1. 빌드 재현이 모든 것에 선행한다

**바꾼 결과가 기존과 같은지 확인할 수 없으면 리팩토링이 아니라 재작성이다.**

지금은 깨끗한 체크아웃에서 부팅 이미지를 만들 수 없다. 이 상태에서 구조를 바꾸면 **"고장난 건지 원래 안 되는 건지" 를 구분할 방법이 없다.**

| 판정 기준 | |
|---|---|
| 통과 | 새 머신에서 체크아웃 → 문서화된 절차 → 플래시 가능한 이미지 |
| 실패 | 어느 한 단계라도 "누구 머신에 있는 파일" 이 필요함 |

**빌드 시스템을 바꾸는 것과 빌드를 재현하는 것은 다른 일이다.** 재현이 먼저다 — 바꾼 뒤 비교할 기준선이 있어야 한다.

## 2. 동작 보존이 성공 기준이다

리팩토링의 정의는 **외부 동작을 바꾸지 않고 내부 구조를 바꾸는 것**이다. 초음파 장비에서 "외부 동작" 은 영상 출력이다.

- 코드 정리 전에 **비교 가능한 기준**을 확보한다 — 동일 입력에 대한 스캔 출력, 프로토콜 패킷 덤프, 측정값
- **사내 선례가 있다.** FPGA 팀은 비트정확 C 골든 모델 + 기대 벡터로 회귀를 잡는다(`ginny-renewal/model/src/*.c`). 장비·앱 쪽에 없는 것이 이것이다
- 기능 추가와 구조 변경을 **같은 커밋에 섞지 않는다**

## 3. 개발 PC 에서 full E2E 가 돌아야 한다

**하드웨어 없이 장비↔앱↔클라우드 전 경로를 개발 PC 에서 검증할 수 있어야 한다.** 이것이 §2(동작 보존)를 실행 가능하게 만드는 유일한 방법이다.

지금은 실장비 없이는 아무것도 확인할 수 없고, 그래서 회귀 판정이 **사람 손에 남는다** — 사내 QA(`[SQA]` 150건) 또는 고객 신고(`moana` 최근 커밋 = 측정 회귀·PACS 밀림·FPS 널뜀)다.

**착수 비용이 낮다** — 프로토콜 정의가 문서화돼 있고, 녹화 포맷·샘플·시나리오 러너가 양쪽 앱에 이미 있으며, 장비 쪽에는 `lib/fpga.cpp` 의 함수 포인터 vtable(`DEVICE_EBI`/`DEVICE_DUMMY`)이 이미 `FpgaPort` 의 골격을 이룬다.

**에뮬레이터는 별도로 만들지 않는다 — `belle-fw` 를 `platforms/pc` 로 가른 결과물이다.** 구성·자산 목록과 각 자산의 한계 = **[emulator-e2e.md](emulator-e2e.md)**.

### 이것이 AI 검증 루프의 전제다

E2E 가 개발 PC 에서 돌면 **AI 가 고치고 → 빌드하고 → 실행하고 → 판정하는 루프**를 사람 개입 없이 돌 수 있다. 지금은 읽고 제안하는 데서 끊긴다([why.md §2](why.md)).

이 조건은 사람에게도 같은 이익이다 — 신규 인력이 장비 없이 첫날 앱을 띄운다.

### 판정 기준

| 통과 | 실패 |
|---|---|
| 실장비 0대로 스캔·측정·DICOM·클라우드 등록까지 회귀 테스트가 CI 에서 돈다 | "이건 장비 연결해서 봐야 안다" |

**이 요구사항이 §1(빌드 재현)과 짝이다.** 빌드가 재현되고 E2E 가 개발 PC 에서 돌면, 그때부터 리팩토링은 안전한 작업이 된다.

## 4. 축을 하나씩 움직인다

장비 · 앱 · 클라우드가 **프로토콜과 스키마로 묶여 있다.**

```
HC 프로토콜 포트 변경 → 앱 파라미터(ctrl_port/data_port) → 서버 API → DB 컬럼
```

세 축을 동시에 바꾸면 문제 발생 시 원인을 가를 수 없다. **한 축을 바꾸는 동안 나머지 둘의 인터페이스는 고정한다.**

## 5. 되돌릴 수 있는 단위로 낸다

**belle 은 이미 A/B 이중 뱅크를 갖고 있다** — 커널(mtd2/3) · 앱 오버레이(mtd4/5). `upgrade.sh` 가 현재 뱅크를 읽어 반대편에 쓴다.

이 구조를 **살리고 활용한다.** 리팩토링 산출물도 같은 경로로 배포해 현장 롤백 가능성을 유지한다.

## 6. 정본은 하나만 둔다

같은 정의가 여러 곳에 복제돼 있는 것이 이 코드베이스의 가장 반복적인 문제다.

| 대상 | 현황 |
|---|---|
| HC 프로토콜 헤더 | 식별자가 **저장소 9곳**에 흩어짐, 구조체 선언은 3벌(`belle-fw`·`moana`·`500c-sn-fw`) |
| 프로토콜 클라이언트 | `moana`·`cuattro-sdk`·`sonex-framework` **3벌** |
| NextSRI 필터 | `moana`·`sonex-framework` **2벌** (그들 문서가 "1:1 포팅, 바이트 동일" 로 기록) |
| 계정 도메인 | Java 백엔드 · Firebase **2벌** |
| 설정 테이블 | `ginny-table` ↔ `elsa-fw/configs` **31파일 MD5 동일** |

**복제본을 지우기 전에 정본을 정한다.** 정본 없이 하나를 지우면 다른 하나가 조용히 갈라진다.

## 7. 사내 선례를 외부 사례보다 우선한다

**더 나은 구조가 이미 사내에 있었다가 버려진 사례가 있다.**

| 항목 | 이전 세대 | 현행 belle |
|---|---|---|
| 변종 선택 | **런타임** — u-boot 환경변수로 5개 모델 선택, 시리얼로 보드 리비전 자동 판별 | **컴파일 타임** — `-D_USING_500L_DEV_` |
| 결과 | **단일 유니버설 이미지** | 모델당 별도 빌드 |

리팩토링 제안의 근거로 cctv-platform 이나 업계 관행을 들 필요가 없다. **`ginny-fw` 가 그렇게 했다** 로 충분하다. 조직 수용성도 높다.

## 8. 브랜치 대신 코드로 변종을 표현한다

인증·국가·고객사·하드웨어 리비전을 **브랜치로 영구 분기**하는 것이 현행 관행이다(`ginny-fw` 는 브랜치 29개 중 6개만 병합).

**규모를 실측했다** — `moana` 커밋 5,705건 중 **712건(12%)** 이 출하 브랜치에 도달하지 못했고, 그중 **329건이 국가·고객사·인증 분기**에 갇혀 있다. 살아있는 분기다(`oem_sphera` 2025-05-28). 상세 = [../review/change-cost.md](../review/change-cost.md) §2.

> **다만 전부가 대상은 아니다.** 인증 브랜치(`500L_Cetification` 68 · `310C_China_Certification` 22)는 인증본 동결이 규제 요구일 수 있어 **우리가 판단하지 않는다.** 단종 라인 142건도 범위 밖이다. 이 원칙의 적용 대상은 **국가·고객사 OEM 분기**다.

**비용이 이미 발생했다** — `moana` 에 `HC_RELEASE_TARGET` 미설정 시 qmake 가 hard-error 를 내도록 강제한 커밋이 있고, 사유는 **CE/US 빌드가 뒤바뀌어 출하된 사고**다.

변종은 **설정·플래그·런타임 선택**으로 표현하고 브랜치는 개발용 단기 분기로만 쓴다.

## 9. 규제를 설계 입력으로 다룬다

의료기기 SW 라이프사이클(IEC 62304)이 요구하는 것과 리팩토링이 만나는 지점이 있다.

| 요구 | 리팩토링에서의 의미 |
|---|---|
| 소프트웨어 항목 식별·구성관리 | **재현 가능한 빌드가 곧 구성관리다**(§1) |
| 변경 영향분석 | 축을 하나씩 움직이는 이유(§4) |
| 검증 기록 | 자동 테스트·CI 가 곧 기록이다 |
| SOUP 관리 | 벤더 라이브러리 버전·출처를 명시해야 한다 — 지금은 **7.2GB 가 커밋된 바이너리**로만 존재 |

**규제 대응과 리팩토링이 상충하지 않는다.** 오히려 같은 것을 요구한다.

> 주의 — **규제를 변경의 장벽으로 쓰지 않는다.** 이 프로젝트는 애초에 리팩토링이므로 검증 비용은 이미 계상돼 있다. "재검증이 필요하다" 는 이유로 필요한 구조 변경을 미루면, 규제가 아니라 관성이 결정을 내리는 것이다.

## 10. 하지 않을 것

| 항목 | 이유 |
|---|---|
| 단일 코드베이스를 플랫폼별로 쪼개기 | `moana`·`sonex` 둘 다 하나의 코드베이스로 모바일·데스크톱을 낸다. 쪼개면 중복이 생긴다 |
| 단종 라인 정리 | 300 시리즈·500C 는 범위 밖. 손대면 회귀 위험만 는다 |
| 대체될 코드베이스라고 방치하기 | `moana` 는 앞으로도 수년간 출하되고 **`sonex` 가 참조하는 사양 원본**이다. 먼저 정리해야 이식이 기계적 작업이 된다([architecture.md §4.3](architecture.md)) |
| 기준선 없이 동작을 바꾸기 | 비교 대상이 없으면 회귀를 판정할 수 없다(§1). 단 **빌드 시스템 교체는 여기 해당하지 않는다** — 그것이 재현을 만드는 방법이다 |

## 11. 기대 효과

| 원칙 | 효과 | 측정 방법 |
|---|---|---|
| §1 빌드 재현 | 신규 인력이 하루 안에 빌드 가능. 하드웨어 리비전 대응 가능해짐 | 깨끗한 머신에서 이미지 생성 성공 |
| §2 동작 보존 | 회귀 판정을 자동화한다. 현재는 사내 QA(`[SQA]` 150건)와 CS 로 잡는다 — **자동 판정만 없다** | 회귀 테스트 통과율 |
| §8 브랜치 정리 | 같은 기능의 재적용을 없앤다. Power Doppler 는 출하 계통 **3곳에 각각** 적용됐고 patch-id 가 전부 다르다 | 중복 patch-id · 출하본 미도달 커밋 수 |
| §6 정본 단일화 | 프로토콜 변경 1회 작업량이 7곳 → 1곳 | 동일 정의의 사본 수 |
| §7 런타임 변종 | 모델당 빌드 → 단일 이미지. 출하·검증 대상이 N → 1 | 릴리스 아티팩트 수 |
| §8 브랜치 정리 | CE/US 뒤바뀜 같은 사고 구조적 제거 | 미병합 장수 브랜치 수 |
| §9 규제 정합 | 62304 문서화 부담이 개발 산출물로 자동 충당 | — |
| §1+§3 합 | **AI 가 고침→빌드→실행→판정 루프를 사람 개입 없이 돈다** | 사람 개입 없이 닫힌 작업 비율 |

## 12. 성공/실패 판정

**성공**: 깨끗한 체크아웃에서 빌드 → 기존과 동일한 스캔 출력 → A/B 뱅크로 배포 → 문제 시 롤백. 이 사이클이 자동으로 돈다.

**실패 신호**: "이 파일은 누구 머신에 있다" · "이건 원래 안 되던 건데" · "브랜치를 하나 더 팔까요".
