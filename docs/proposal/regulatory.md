# 규제 — 요구항목과 산출물 대응

> [README.md](README.md) §5 의 상세. **판단 주체는 힐세리온이다.** 이 문서는 우리가 만드는 산출물이 어느 요구에 대응하는지 정리한 것이지, 적합성 판정이 아니다.
>
> 조항 번호는 IEC 62304 (2006 + A1:2015) 기준의 **참조용**이며, 확정은 귀사 RA 의 몫이다.

## 0. 전제 — 우리가 하지 않는 것

| | |
|---|---|
| 안전등급 판정 (Class A/B/C) | **귀사** |
| 재검증 범위 결정 | **귀사** |
| DHF·QMS 반영 | **귀사** |
| 인증기관 대응 | **귀사** |
| 위 판단에 필요한 기술 산출물 생성 | 우리 |

**그리고 중요한 구분 하나** — 이 검토는 코드 저장소만 봤다. **저장소에서 확인되지 않았다는 것이 귀사 QMS 에 없다는 뜻이 아니다.** 설계이력·위험관리 파일·검증 기록이 Phriction 이나 별도 QMS 에 있을 수 있고, 우리는 그것을 보지 못했다. 아래 §3 은 "규제 위반" 목록이 아니라 **"저장소만으로는 추적되지 않는 항목"** 목록이다.

## 1. 안전등급이 먼저다

재검증 범위는 안전등급에서 갈린다. 진단용 초음파 영상은 통상 진단 정보를 제공하므로 Class B 이상으로 다뤄지는 경우가 많으나, **이것은 제품 위험분석의 결론이지 우리가 정할 수 있는 것이 아니다.**

등급이 확정되어야 다음이 정해진다.

| 등급에 따라 달라지는 것 | 이 제안에 미치는 영향 |
|---|---|
| 아키텍처 설계 문서화 요구 수준 | 5단계(구조 변경)의 산출물 형식 |
| 단위 검증 요구 | 4단계(CI)에서 무엇까지 자동화할지 |
| SOUP 위험 통제 요구 | 7.2GB 프리빌트 라이브러리의 처리 방식 |
| 통합·시스템 시험 요구 | E2E 시나리오의 범위 |

**요청 항목**: 현재 belle(500L) 계열의 안전등급과, 기존 인증 시 제출한 소프트웨어 문서의 범위.

## 2. 요구 ↔ 산출물 대응

이 작업이 만드는 것이 규제가 요구하는 것과 겹치는 지점이다. **부산물이지 목적이 아니다** — 규제 문서를 대신 써 드린다는 뜻이 아니라, 기술 근거가 자동으로 남는다는 뜻이다.

| 요구 영역 (참조 조항) | 요구하는 것 | 이 작업의 산출물 | 단계 |
|---|---|---|---|
| **구성관리** (8.1 구성 항목 식별) | 소프트웨어 항목과 버전을 식별할 수 있을 것 | 재현 가능한 빌드 정의 — 어느 소스가 어느 이미지가 되는지 | 2 |
| **SOUP** (5.3.3~5.3.4, 8.1.2) | 제3자 소프트웨어의 명칭·제조자·버전 목록 | 의존성 매니페스트 (출처·버전·해시) | 2·7 |
| **변경 통제** (8.2) | 변경 요청 → 승인 → 검증의 추적 | 커밋 ↔ 리뷰 ↔ CI 실행의 연결 | 4 |
| **구성 상태 기록** (8.3) | 각 릴리스에 무엇이 들어갔는지 | 빌드 산출물과 소스 리비전의 고정 | 2·4 |
| **검증 기록** (5.5~5.7) | 단위·통합·시스템 시험 결과 | CI 실행 이력, E2E 시나리오와 결과 | 3·4 |
| **아키텍처 설계** (5.3) | 소프트웨어 항목 간 인터페이스 명세 | 프로토콜 정본 1벌 — 인터페이스가 코드로 단일화된다 | 1 |
| **문제 해결** (9) | 문제 기록·분석·검증 | 데이터 경로 회귀가 커밋 시점에 잡히면 기록이 남는다 | 4 |
| **위험 관리** (7) | 소프트웨어 기여 위험의 식별·통제 | 구조 작업 자체는 위험을 식별하지 않는다 — **귀사 몫** | — |

마지막 줄을 명시해 둔다. **위험 관리는 우리 산출물로 대체되지 않는다.**

## 3. 저장소만으로는 추적되지 않는 항목

사실 관찰이다. 앞서 말했듯 QMS 에 별도로 있을 수 있다.

| 관찰 | 대응 단계 |
|---|---|
| 검토한 31개 저장소에 CI 파이프라인이 없다. 자동 테스트는 `sonon-cloud`·`sonex-app`·FPGA 골든 모델 3건에 존재하나 실행 체계가 없다 | 4 |
| 깨끗한 체크아웃에서 부팅 이미지가 나오지 않는다 (`petalinuxbsp.conf:15` 이 `/home/jacob/...` 절대경로) | 2 |
| 서드파티 프리빌트 7.2GB 의 출처·버전이 저장소에 기록되어 있지 않다 (`moana/lib` 6.1G · `sonex-framework/sdk/adk/library` 1.1G) | 2·7 |
| 커널 모듈 3종(`plif`·`zynqdma`·`msp430_drv`)의 빌드 파일이 없다 | 2 |
| 힐세리온이 작성한 belle 계열 저장소(`belle-fw`·`belle-bsp`·`belle-msp`)에 README 가 없다 | 2 |
| 장비↔앱 프로토콜에 CRC·체크섬이 없다. 함수명은 `verify_packet_header_and_crc` 이나 검사 코드가 없다 | 별도 판단 |
| `recv_id` target 검사가 도달 불가 코드다 ([../refactoring/proof/protocol-sot/](../refactoring/proof/protocol-sot/) §recv_id) | 1 에서 기록, 수정은 별도 승인 |

마지막 두 항목은 **동작 변경**이므로 1단계 범위에 넣지 않았다. 기록만 하고 처리 여부는 귀사 판단에 맡긴다.

## 4. 단계별 재검증 트리거

| 단계 | 제품 동작 변경 | 바뀌는 것 | 재검증 성격 |
|---|---|---|---|
| 0 비밀정보 교체 | 없음 | 운영 자격증명 | 제품 SW 외 |
| **1 프로토콜 정본** | **없음 — 컴파일러로 증명** | 헤더 파일의 위치. 값·이름·바이트 배치 전부 동일 | 소스 구성 변경. 빌드 산출물 동일성 대조로 확인 가능 |
| 2 빌드 재현 | 없음 (목표) | 빌드 시스템 | **기존 이미지와의 대조가 판정 기준.** 산출물이 달라지면 그것이 발견 대상이다 |
| 3 개발 PC 어댑터 | 없음 | 플랫폼 계층 추가. 장비 경로는 그대로 | 실장비 동작 동일성 |
| 4 E2E·CI | 없음 | 검증 체계 추가 | 제품 SW 변경 아님 |
| **5 구조 변경** | **있음** | 코드 배치 | **전면 대상.** 그래서 1~4 뒤에 온다 |

**1단계가 "동작 불변"인 근거는 주장이 아니라 실행 가능한 검증이다** — `make` 가 원본 3벌과의 바이트 배치 동일성, 원본 상수 198개의 값 보존, 실제 패킷의 검증 통과를 판정한다.

## 5. 우리가 답할 수 없는 것

- 현재 belle 계열의 안전등급과 기존 인증 제출 범위
- 변경 이력·검증 기록의 소유 주체 (위탁 수행분의 기록을 누가 보관하는가)
- 리팩토링 산출물을 기존 DHF 에 편입하는 방식
- MFDS·FDA·CE 각각에 대한 변경 신고 필요 여부

**여기에 답을 지어내지 않는다.** 이 항목들은 착수 전 합의 대상이다.
